# HW04 Traceability and Planned Automated Test Matrix — Student 23127027

## Scope and status

This is a test-design artifact for the web and backend API only. It contains exactly 36 planned automated cases and excludes `frontend-mobile` plus every HW02 test case and result. No case in this document has been executed; no pass/fail result is claimed.

The three planned external data sources are:

- `tests/data/fr01-registration.json` for registration inputs, generated unique-email templates, and validation partitions.
- `tests/data/fr07-cart.json` for seeded product/cart states, quantities, prices, and cleanup identifiers.
- `tests/data/fr12-access-control.json` for token classes, protected-route inventory, controlled mutation payload references, and backup/restore identifiers.

Automation specs must load named records from those files. They must not declare inline test-case arrays or objects. Secrets and live JWTs must come from the test environment or authenticated setup, not be committed to the data files.

## Evidence hierarchy

1. `README.md`, version 2.0 (updated 2026-05-14), is the authoritative requirements source.
2. `api_specification.md` is supporting contract evidence for documented endpoints, methods, headers, bodies, and the one explicit registration-success response.
3. An expectation absent from both documents is marked **EVIDENCE MISSING**; the automation must not invent an exact status code, message, redirect URL, schema, or browser-specific behavior.
4. A requirement/contract mismatch is a discrepancy **test target** until execution evidence exists. It is not a confirmed defect in this plan.

## Assertion pattern legend

- **A11Y-ROLE/TEXT** — locate by semantic role/accessible name and assert visibility, exact required text, or element count.
- **DOM-ATTR/STRUCTURE** — assert element attributes, heading count, table structure, image `alt`, or required-marker placement.
- **NAV/FOCUS** — assert URL/page transition, active navigation state, breadcrumb, or keyboard focus sequence.
- **GEOMETRY/STATE** — assert relative UI position or before/after visible state without relying on implementation classes.
- **VISUAL-STYLE** — assert a requirement-level visual category from computed style (for example, blue positive action or red dangerous action); an exact shade is not asserted unless specified.
- **API-STATUS/BODY** — assert the documented status/body where available; otherwise assert only rejection/success class and label exact details **EVIDENCE MISSING**.
- **STATE-DELTA** — compare authoritative pre/post UI or API state, counts, quantities, totals, or persisted fields.
- **DENY-NO-MUTATION** — assert access is denied and a pre/post snapshot is unchanged.
- **CROSS-CHECK** — verify the same business state through an independent UI/API read-back or a fresh authenticated session.

## Execution policy

- These are planned automated checks only. Before execution, create the three external JSON files listed above and keep all test vectors, route inventory records, and payload variants there; spec files may reference row keys but must not contain inline case arrays or objects.
- Run UI cases in isolated Chromium, Firefox, and WebKit projects. API cases may run once per browser project through its request context; their expected behavior is browser-independent, and browser-specific differences must not be invented.
- Generate collision-safe emails and fixture identifiers at runtime from external templates. Use dedicated test users, deterministic products/categories/coupons, and least-privilege tokens.
- Capture baseline state before every mutation. Use normal application/API cleanup when it is explicitly safe; otherwise use a controlled database backup/restore. Teardown must run even after assertion failure, and cleanup failures must be reported separately from product assertions.
- For denial tests, verify both the rejection and absence of state change. Never infer authorization merely from hidden UI controls; direct protected API requests are required.
- Do not convert an observed implementation/specification difference into a confirmed defect without execution evidence, reproducible actual results, and comparison against the README v2.0 oracle.
